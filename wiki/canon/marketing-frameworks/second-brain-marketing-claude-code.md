# Second Brain маркетолога — система принятия решений на Claude Code

«Второй мозг» (Second Brain) для маркетинга — это не хранилище данных, а **система принятия решений**. На входе — сырьё (креативы, данные кампаний, исследования клиентов, инсайты по конкурентам, транскрипты глубинных интервью). На выходе — конкретный план действий: набор офферов для теста, отсортированные гипотезы, список изменений в рекламных кабинетах.

Источник: Kumar & Solo (Р. Кумар Виас и А. Соловьёв, founders Refocus DE), [[sources/2026-05-30-tg-solokumi-may-27-29-2026|@solokumi]] пост 420 (2026-05-27).

Это `canon`: сама архитектура (vault + декомпозиция компонентов + правило «правильный срез контекста») — стабильная инженерная рекомендация на всю эпоху IDE-агентов. Конкретные инструменты (Obsidian, Claude Code) — дрейфующий слой, но методология от них не зависит.

## Зачем

У маркетолога обычно есть всё, что нужно для качественных решений — но человеческая «коробка с мозгом» не успевает качественно проанализировать массив данных и сделать верные выводы. В маркетинге ошибка стоит дорого. Second Brain снимает этот bottleneck: данные превращаются в систему, которая отвечает на оперативные вопросы.

**Кому в команде Kumar & Solo собрали/собирают 2nd brain:**

| Роль | Что трекает Second Brain |
|---|---|
| **Фаундеры** | Ключевые бизнес-метрики (runrate по выручке/CPL, отвалы в продукте) + сигналы по просроченным таскам и критическим точкам уязвимости (work in progress) |
| **Маркетологи** | Маркеры выгорания креативов/воронок + конкретный план действий по исправлению + трекинг выполнения плана и сигнал, если вываливаемся из runrate |

## Ключевой принцип — правильный срез контекста, а не весь массив

Главное правило построения Second Brain: использовать **не весь массив данных, а только правильный кусок контекста**. Если дать слишком много нецелевых данных на вход, контекст заполнится, сессия деградирует, и результат будет плохой.

Это тот же инвариант, что лимит 200 строк в [[canon/marketing-frameworks/claude-md-structure-marketing|CLAUDE.md structure]]: после определённого объёма модель перестаёт уделять внимание релевантному. Архитектура Second Brain (раскладка по папкам, компонентная декомпозиция) существует именно чтобы можно было подать агенту **узкий релевантный срез**, а не весь vault целиком.

## Декомпозиция креатива на компоненты

Скрин рекламы конкурента сам по себе бесполезен. Ценность появляется, когда крео **размечено по компонентам**:

**Персона / Боль / Хук / Оффер / CTA / Результат**

Когда эти данные собраны, Claude собирает новое крео из компонентов, которые **уже работали**. Критично: в базу нужно класть и **провалы** — хуки, которые не удержали внимание; офферы, которые не дали заявку; CTA, которые убили конверсию. Без негативных примеров система не отличает работающий компонент от случайно выстрелившего.

Эта декомпозиция — операционный мост между «архив скринов» и «генератор гипотез»: единица знания — не крео целиком, а отдельный переиспользуемый компонент с привязкой к результату.

## Структура vault (Obsidian)

Vault — папка в терминологии Obsidian. Все файлы — обычные локальные markdown, поэтому Claude Code читает их напрямую без настроек.

```
second-brain/
├── 00_raw/            ← всё сырьё: старые крео, скрины конкурентов, заметки с созвонов, отчёты
├── 01_components/     ← размеченные компоненты (Персона/Боль/Хук/Оффер/CTA/Результат)
├── 02_creatives/      ← собранные креативы
├── 03_performance/    ← данные эффективности
├── 04_competitors/    ← конкуренты
└── 05_brand_context/  ← бренд-контекст
```

`CLAUDE.md` в корне vault — файл правил, который Claude Code читает при каждом запросе: где что лежит, кто аудитория, в каком формате хранятся компоненты, что нельзя выдумывать. Детали структуры самого файла — в [[canon/marketing-frameworks/claude-md-structure-marketing]].

## Рабочий цикл

1. В `00_raw/` закидывается всё, что есть.
2. Claude разбирает и раскладывает по папкам (в т.ч. размечает крео на компоненты).
3. Подключаются трендвотчинг и скрейперы («пылесосы внешних данных»).
4. Базе можно задавать **реальные вопросы**:
   - «5 вариантов хука на эту персону на основе тех, у которых лучший CPL»
   - «какие креативы у конкурентов крутятся дольше 2 месяцев»
   - «какие CTA всегда сливают конверсию»

Чем больше материала накапливается, тем точнее ответы. Это прямая иллюстрация рамки [[canon/marketing-frameworks/quantity-over-quality-iteration-ulsmann|количество → качество]]: ценность Second Brain растёт как функция объёма размеченного опыта, а не разовой настройки.

## Связь с многоагентной оркестрацией

Second Brain — это **хранилище и слой запросов**, на котором работают агенты из [[canon/marketing-frameworks/multi-agent-marketing-org-principles|5 принципов оркестрации]]. Сенсоры (слой 1) пополняют `00_raw/`, аналитики (слой 2) задают базе вопросы и генерируют гипотезы, исполнители (слой 3) собирают крео из компонентов. Без общего vault'а агенты не имеют разделяемого контекста, и каждый стартует «с комы».

## Что это значит для GRO

1. **Применимо к самому GRO как инструмент маркетинга**: собрать vault с компонентной декомпозицией собственных крео (Персона/Боль/Хук/Оффер/CTA/Результат) и крео конкурентов в нише productivity/self-improvement.
2. **Негативная база критична**: для GRO важно класть провальные хуки и офферы — категория эмоционально нагружена (мотивация, дисциплина), легко повторить не-работающий ход.
3. **Связка с данными звонков/поддержки** (см. [[evolving/content-trends/sales-calls-as-marketing-dataset-2026]]): транскрипты обращений пользователей — топливо для `01_components/` (реальные боли → хуки).
