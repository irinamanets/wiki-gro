# Stanford-исследование вайбкодинга — методологическая рамка и 9× правило уязвимостей

**Источник:** препринт Stanford `arxiv 2604.20779` (опубликован к маю 2026), пересказан и интерпретирован Байрамом Аннаковым в посте 1740 ([[sources/2026-05-14-tg-products-and-startups-may-2026]]). Это **первое количественное исследование** поведения разработчиков с coding-agents в полях, основанное на публичных репозиториях.

## Что это и зачем эта страница в marketing-frameworks

Сам пейпер — инженерный. Но для marketing-memory он критичен по трём причинам:

1. **Numerical proof-points для контента**: до Stanford все тезисы про «harness > prompt > model» опирались на personal opinion (Бай, Карпатый, Anthropic). После Stanford — это **измеренные числа на 6 000 сессий**. Меняется доверие к нарративу.
2. **Каноническая структура research → content hook**: как переводить инженерный пейпер в маркетинговые тезисы (см. раздел «Применение к контенту» ниже).
3. **9× правило уязвимостей** — самый сильный hook для anti-FOMO контента про автономный AI-дев. Reusable формулировка: «Чистый вайбкодинг создаёт security-уязвимости в 9 раз чаще, чем человек руками».

Числа же сами по себе живут в [[evolving-strict/competitor-metrics/stanford-vibecoding-stats-apr-2026]] (`*-strict` layer, обновляется при выходе новых пейперов).

## Методология исследования

| Параметр | Значение |
|---|---|
| Период сбора данных | январь–апрель 2026 |
| Сессий | 6 000 |
| Промптов | 63 000 |
| Тулколлов | 355 000 |
| Источники сессий | Claude Code (большинство, Opus 4.6), OpenCode, Gemini, Factory |
| Тип репозиториев | публичные репы (GitHub-style) — энтузиасты, опен-сорс, прототипы |

**Важные дисклеймеры (озвучены Баем):**

1. Датасет — публичные репы. Прод-код Stripe / банков туда не попадает.
2. Stanford использовал **Semgrep** для детекции уязвимостей — ловит **паттерны**, не реальную exploitability. Часть алертов — ложные срабатывания.
3. **Коммит ≠ прод.** CI, PR-ревью, security-сканеры ловят часть до релиза. Пейпер смотрит на коммит.
4. **Self-selection bias:** вайбкодинг чаще на greenfield/прототипах, ручной код — на проде.

«Цифру 9× надо читать как **грубый порядок**, а не точную меру. Но направление и порядок величины — реальные.» — Бай.

## Три раздела результатов

### Раздел 1 — Use cases coding-агентов (RQ1, Sec. 3.1)

Распределение интентов в 6 000 сессий:

| Use case | Доля |
|---|---|
| Code **understanding** | **19%** (наиболее частый) |
| Git operations | 14% |
| Create new code | 13% |
| Debug | 13% |
| Refactor | 9% |
| Other | 32% |

**Маркетинговое наблюдение:** «понимание кода» обгоняет генерацию. Это flips популярный нарратив «AI пишет код». На самом деле AI чаще объясняет код. Это **хук** для аудитории, которая боится «AI заменит программиста»: в реальности AI = собеседник по чтению, не автор.

**Tool calls distribution:** `bash` 33%, `read/edit/search files` 48%, прочее ~19%. Это объясняет, **почему harness важнее модели**: модель проводит большую часть времени на чтении файлов и баш-командах, а не на «думанье».

### Раздел 2 — Vibecoding is trending (RQ1, Sec. 3.2)

| Режим работы | Доля сессий |
|---|---|
| Чистый вайбкодинг (агент пишет >99% кода) | **41%** |
| Чистый human (человек пишет всё) | 23% |
| Гибрид | ~36% |

**Survival rate сгенерированного агентом кода (до коммита):**

| Режим | Survival rate |
|---|---|
| Коллаборация | **44%** |
| Чистый вайбкодинг | **59%** |

Парадокс: чистый вайбкодинг даёт **более высокий survival rate**. Авторы пейпера трактуют это двояко: либо «лучшее попадание в задачу», либо «просто меньше ревью со стороны юзера». Бай склоняется ко второму: «по моему личному опыту, каюсь, это скорее второе.»

**Code waste breakdown** (того, что не доживает):
- ~10% — агент сам же переписывает (черновики)
- ~46% — юзер удаляет или переписывает руками

Хук Бая ([[evolving/content-trends/ai-product-engineer-content-hooks]]): «каждая вторая строчка дружбана идёт в мусор, и решение оставить или нет — это наша когнитивная нагрузка».

### Раздел 3 — User behavior во время вайбкодинга (RQ1, Sec. 3.3)

Типизация юзеров:

| Тип | Доля |
|---|---|
| Expert Nitpicker (детальные правки) | 40% |
| Vague Requester (размытые требования) | 33% |
| Other | 20% |
| Mind Changer (часто меняет план) | 7% |

В чистом вайбкодинге **mind-changing меньше** — паттерн похож на «отпустил руль».

## Раздел 4 — Где агенты падают (RQ2)

### Sec. 4.1 — Session success rate

**Средний success rate сессии — 82%.** Fail-сценарии:

1. Юзер прерывает (interrupt)
2. Системная ошибка блокирует агента

### Sec. 4.2/4.3 — Costly, slow, unsafe

Pricing per 100 committed lines (медиана):

| Режим | Цена |
|---|---|
| Human-only | $0.07 |
| Collaborative | $0.05 (меньше всех!) |
| Vibe coding | $0.13 (в **2.6×** дороже collaborative) |

**Парадокс:** коллаборация дешевле чистого human. Объяснение: при коллаборации **меньше попыток**, потому что AI ускоряет, а человек контролирует.

### Sec. 4.4 — Agents rarely stop, users push back

| Событие | Доля turns |
|---|---|
| Agent stop (агент сам остановился задать вопрос) | **1%** |
| User interruption | 5% |
| User pushback (юзер не согласен с агентом) | **41%** |

**Хук:** «Агенты редко останавливаются. Юзер не соглашается в 41% реплик.» Это сильнейшая иллюстрация необходимости **harness'а с self-review** (см. [[canon/marketing-frameworks/harness-engineering-for-ai-agents]] раздел 3 «дайте агенту зеркало»).

## Главный результат — 9× правило уязвимостей

**Vulnerability rate, на 1 000 строк введённого кода:**

| Режим | Vulnerabilities / 1K LOC | Относительно human |
|---|---|---|
| Человек руками | **0.08** | baseline (1×) |
| Человек + агент в коллабе | **0.14** | ~1.8× |
| Чистый вайбкодинг | **0.76** | **~9.5×** |

Конкретный пример из пейпера: агент написал `subprocess.run(cmd, shell=True)` — классический **CWE-78, command injection**. Гипотеза Бая о причине: «такое чаще встречается в тренинг-датасете».

### Контент-хуки из 9× правила

1. **«В 9 раз больше уязвимостей»** — короткая, запоминающаяся, измеренная цифра. Reusable во всех постах про «AI не заменит инженеров безоговорочно».

2. **«Чистый вайбкодинг не дешевле — он дороже в 2.6×»** — переворот популярного нарратива «AI делает дёшево». Stanford пишет: median $0.13 vs $0.05 на 100 committed lines.

3. **«Loss Disguised as a Win»** — связь с framework slot-machine ([[canon/marketing-frameworks/slot-machine-vs-printer-genai-strategies]]). Скорость вайбкодинга ощущается как победа, через неделю выясняется что в 9 раз больше уязвимостей.

4. **«Кстати, я даже не помню что я просил вайбкодеру»** — связь с [[evolving/industry-trends/ai-cognitive-atrophy-identity-2026]] (comprehension debt).

## Что с этим делать — рекомендации Бая

Бай выводит из исследования те же 4 рекомендации, что уже зафиксированы в [[canon/marketing-frameworks/harness-engineering-for-ai-agents]]:

1. **Опасные операции блокируются СИСТЕМНО — архитектурой, потом сканерами.** Capability scoping (агенту физически недоступны деструктивные операции), credential isolation (токены с минимальным набором прав), бэкапы **вне** доступности агента. **Кейс Jer Crane** (фаундер PocketOS): добавил в системный промпт `NEVER FUCKING GUESS!` + правило не делать деструктивные операции — агент всё равно снёс продакшн-базу вместе с бэкапами (Railway хранит бэкапы на том же volume). Инструкций недостаточно — нужна **физическая невозможность**.

2. **«Швейцарский сыр» защиты** (Anthropic engineering blog, demystifying evals for AI agents): 3+ уровня проверки, каждый ловит то, что пропустили другие.

3. **Plan Mode на каждой нетривиальной задаче.** Если 44% генерации идёт в мусор — обсуждай план **до** написания кода, а не после.

4. **Reflection с security-линзами.** Каждое утверждение агента про «я сделал X» — повод заставить его проверить «а действительно я сделал X безопасно?».
