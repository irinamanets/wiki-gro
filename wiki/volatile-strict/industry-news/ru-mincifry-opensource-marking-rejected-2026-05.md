# Минцифры отказалось от обязательной маркировки отечественного ПО с открытым кодом

Минцифры РФ **отложило проект по введению обязательной маркировки отечественного ПО с открытым кодом**. `[conf:high, src:2026-05-05]` Прямая цитата представителя министерства: «Определить минимальную долю использования открытого кода в составе ПО представляется затруднительным». `[conf:high, src:2026-05-05]` Через [[sources/2026-05-05-tg-forbesrussia-may-4-5-2026|@forbesrussia 95647]].

| Заявленная причина | методология определения «минимальной доли open-source кода» — непрактично | `[conf:high, src:2026-05-05]` |

## Что это означает

**1. Регуляторика становится точечной, не универсальной.** Идея «маркировать всё ПО по доле open-source» была попыткой создать **универсальный лейбл**, как у пищевой промышленности. Признание невозможности фиксации «доли open-source» — операционный provал универсального подхода. **Сигнал**: будущая регуляторика будет per-категория (например, AI-модели через ФСТЭК+ФСБ — см. [[evolving/industry-trends/ru-ai-national-strategy-2026]]), а не общая.

**2. Снимает административное давление с разработчиков.** Маркировка означала бы дополнительную compliance-нагрузку (audit кодовой базы, заполнение реестров, периодическая re-сертификация). Отказ — net positive для **российского software-business**, особенно для SaaS (включая [[canon/product-knowledge/gro-app-overview|GRO]]), который часто использует open-source-стек.

**3. Расхождение с трендом «защитить отечественное».** В то же время идёт регулирование AI на госданных (см. [[evolving/industry-trends/ru-ai-national-strategy-2026]]) и метерики VPN (см. [[volatile-strict/industry-news/ru-vpn-metering-proposal-2026-04]]). **Регуляторика стала "selective"**: жмут там, где может быть стратегический leverage, отпускают там, где нет техники проверки. `[conf:medium, src:2026-05-05]`

**4. Методологический сигнал — open-source трудно определять.** Это **общая проблема индустрии** — где граница «open-source ПО» vs «proprietary с open-source-зависимостями» (например, npm-пакеты)? Российский регулятор честно признал operational invariant: формальная классификация невозможна без massive overhead. **Это разумная позиция** для деловых клиентов, кто опасался «у нас в стеке лежит React — теперь надо сертифицироваться?».

## Что это значит для GRO

**Прямое следствие — нет:** GRO не подавало заявку на маркировку open-source ПО, нет нагрузки.

**Косвенное:**

- **Снижение системного «regulatory creep» риска** — параметр на фоне VPN-метерики, Telegram-ограничений, мобильного интернета 5–9 мая. **Не каждый regulatory сигнал → закручивание гаек**: некоторые отказы возможны, если методологически нереалистично.
- **Положительный signal для B2B-клиентов GRO** — российские клиенты не теряют compliance-burden на свой технологический стек, что снимает потенциальные опасения по поводу AI/SaaS-интеграций.
- **Хук для контента**: «когда регулятор сам признаёт, что определить открытый код невозможно, вы можете спокойно работать со стандартным стеком» (для постов про AI-инфраструктуру).
